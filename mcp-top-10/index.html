MCP / AI-tool security

The MCP Security Top 10

The Model Context Protocol wires LLMs and agents into real tools, data, and credentials. The risks that actually bite are not exotic - they are the boring, high-blast-radius ones that recur across almost every gateway and server. This is our working Top 10, ranked by business impact, not by CVSS.

Updated 2026-10-29 · Securva AI/MCP security practice · Questions: hello@securva.net

How to read this

An MCP server or AI gateway is, in security terms, a credential store with an API in front of it. It holds the keys and OAuth tokens your agents use, routes to every tool and data source you have connected, and is often stood up by one engineer with no security review. That is why a single weak default here is rarely "one bug" - it is org-wide blast radius: theft of every credential the component holds, access to every system those credentials reach, and in multi-tenant setups, cross-customer exposure.

Each entry below is: what it is, why it matters in business terms, and a one-line check / mitigate. We rank by realistic impact on revenue and data at organizations that actually have budget - a medium-severity flaw in a payment-adjacent agent outranks a high-severity one in software nobody runs. This is a living document; we revise it as the protocol and the deployments mature.

The list

A1Session / identity not re-bound on resume
High impactCross-tenant

Many MCP servers and gateways issue resumable sessions keyed by a session ID (for SSE / streamable-HTTP transports, reconnects, long-running agents). The flaw: on resume, the server looks the session up by its ID and serves it without re-checking that the caller is the same authenticated subject the session was created for. Anyone who obtains, guesses, or forges a session ID inherits another user's authenticated session - a confused-deputy at the protocol layer. A sibling failure is signing/encrypting session IDs with a shared or default secret, which lets an attacker forge valid IDs outright.

Why it matters: a session is an authenticated channel to tools and data. Hijacking one means acting as the victim - reading their data, invoking their tools - with full attribution to them. In a multi-tenant gateway this is a cross-customer breach, the worst outcome for a SaaS: mass regulatory exposure and notification cost, and it is hard to detect because the action looks legitimate.

Check / mitigate: on every resume, re-derive the subject from the trusted auth layer (verified JWT / gateway-set header, never the client-supplied bearer alone) and hard-fail on mismatch; use random per-install session secrets, never a shipped default; apply the check uniformly across all transports and verbs. The leading gateways already do this - bind an owner fingerprint to each session and reject on mismatch - so there is no excuse to ship it open.

A2Broken / incomplete authorization coverage
Medium impactData read

The server has an authorization policy (scopes, roles, allow/deny, default-deny), but it is enforced on some MCP methods and silently skipped on others. MCP has several method families - tool calls, tool listing, resource reads, prompt fetches, completion. If the policy is wired into the obvious one (tool calls) but not the siblings (resource reads, prompt fetches), a caller denied at the tool layer can still reach data through the un-policied methods. It is especially dangerous when the docs promise the policy applies to "all requests," so operators configure default-deny and believe the route is locked down.

Why it matters: authentication still gates reaching the server, so this is an authorization-granularity bypass that leaks data, not full unauthenticated access. But on a RAG or data-connected backend, the resources and prompts are exactly the sensitive content the policy was meant to protect. It also fails audits - you cannot attest "least privilege enforced" when enforcement has holes.

Check / mitigate: route every method through a single authorization checkpoint the handlers cannot bypass, not a per-handler check that drifts as methods are added; default-deny and fail-closed on policy errors; where the upstream cannot yet enforce per-method authz, restrict the route to the method set you have actually policied.

A3Unauthenticated or network-exposed endpoints
High impactFull takeover

An MCP server or AI gateway bound to all interfaces with authentication off - either a "dev mode" default shipped to a real network, or a "quick-start" container that binds 0.0.0.0 with no token required. A related variant is a localhost-only service reachable from a malicious web page via DNS rebinding because it does not validate the Host/Origin header.

Why it matters: this is the single highest-dollar risk in the category. An unauthenticated attacker who reaches the endpoint can list and invoke every connected tool, register new tool servers, or read the management API - full control of the org's tool-and-data fabric with no credential. Real-world auth-bypass flaws in self-hosted AI gateways have been serious enough to land on CISA's Known Exploited Vulnerabilities catalog.

Check / mitigate: never run in an auth-disabled mode on a reachable network; bind to loopback or an internal interface behind an authenticating reverse proxy; require the same auth on the MCP/HTTP transport as on the admin API (parity); validate Host/Origin to defeat DNS rebinding; refuse to start, or alarm loudly, when auth is off and the bind is non-loopback.

A4SSRF via tool / connector outbound fetch
High impactCloud creds

A tool or gateway fetches a URL that the caller or configuration influences - an image URL, a webhook, a "fetch this page" tool, a registered server address, an OCI/registry pull - with only a scheme check and no egress controls. The request can be pointed at internal services or at the cloud instance-metadata endpoint (169.254.169.254).

Why it matters: pointing the fetch at instance metadata lets an attacker steal the component's cloud role credentials - and the gateway's role is usually broad. That is a direct path from "my agent can summarize a web page" to "attacker has our cloud account." It is also the most common single class across self-hosted AI gateways today.

Check / mitigate: egress allowlist; block RFC-1918 + link-local + the metadata IP; pin the resolved IP for the life of the request to defeat DNS rebinding; disable or strictly validate redirects; at the instance level, require IMDSv2 with a low hop limit as defense in depth.

A5Excessive agency / over-broad tool scopes
High impactBlast radius

The agent or MCP server is granted far more access than its task needs - a database admin role when it only reads one table, a write-everything OAuth scope when it only posts to one channel, a shell tool when it only needs to read files. This is not a single bug; it is the multiplier that turns every other item on this list from an incident into a catastrophe.

Why it matters: when a prompt-injection or a session hijack lands, the damage equals the union of everything the agent's credentials can touch. The same compromise against a least-privilege agent is contained; against a god-mode agent it exfiltrates the data store or pushes malicious code. Over-privilege is the difference between a near-miss and a breach-notification.

Check / mitigate: enumerate the scopes/roles actually used versus granted; scope tokens per tool, read-only by default, short-lived; put a human-in-the-loop approval on destructive actions; produce a privilege matrix (what each tool can do, what the task requires) and close the gaps.

A6Secrets & tokens in MCP configs (credential sprawl)
High impactCredential theft

Long-lived API keys and OAuth tokens stored in plaintext config files, committed to repositories, synced to dotfile backups, written to logs, or forwarded verbatim to downstream tools. The MCP ecosystem's local-config conventions make this pervasive - the secrets that unlock every connected SaaS tend to sit in a world-readable JSON file.

Why it matters: credential theft is the real monetizable outcome of many otherwise "low" bugs. Any read primitive - a path traversal, an SSRF, a log leak, a stray git history - becomes full SaaS/cloud account takeover the moment it touches the config. This is often the quiet step between a modest finding and a full breach.

Check / mitigate: use a secret manager or OS keychain, not config files; prefer short-lived tokens; never log credentials; scan configs and git history for secrets; restrict and audit any endpoint that can read stored server credentials.

A7Prompt injection via tool output / indirect injection
High impactExfiltration

Untrusted content the agent ingests - a web page, an email, a support ticket, a document, a code comment, or the output of one tool fed into the next - carries instructions the model treats as commands and acts on with the user's own authority. The canonical danger is the "lethal trifecta": access to private data, exposure to untrusted content, and an outbound channel to exfiltrate - present at once.

Why it matters: this is the hardest class to fully fix and the one attackers reach for first, because the injection surface is anywhere untrusted text enters context. The outcome is silent data exfiltration, unauthorized transactions, or poisoned automations, all of which "look legitimate" because the agent did them.

Check / mitigate: there is no single patch - treat it as architecture. Trust-boundary untrusted content away from tool-calling authority; break the trifecta (remove the exfil channel, or require human approval on outbound/sensitive tool calls); never auto-execute tool calls derived from untrusted output; constrain and validate what the model is allowed to do rather than relying on telling it to behave.

A8Unvalidated tool inputs → command / SQL injection
High impactRCE / data

A tool takes model- or user-supplied arguments and passes them into a shell command, a SQL query, a file path, or an eval without validation or parameterization. The LLM is treated as a trusted caller, so classic injection defenses are skipped - but the "caller" is steering on attacker-influenced input.

Why it matters: this is the straight line from "the agent can run a tool" to remote code execution, database compromise, or arbitrary file read/write on the host. Because an agent assembles tool arguments dynamically, inputs a human would never type get generated, so the injection surface is wider than a traditional app's.

Check / mitigate: treat every tool argument as untrusted; parameterize queries, avoid shell string-interpolation (use argument arrays, never a shell), validate and canonicalize file paths, never eval; least-privilege the tool's own execution context so a successful injection is contained.

A9Supply-chain: malicious servers & tool-description poisoning
Medium-high impactSupply chain

Trust placed in third-party MCP servers and in the tool descriptions themselves. Classes include tool poisoning (malicious instructions hidden in a tool's description/schema that the model reads as guidance), rug-pull (a server that mutates its description after you approved it), and tool-shadowing / "line-jumping" (one server's description overriding or intercepting another's tool). The description is untrusted content fed to the model with tool-calling authority - indirect injection delivered through protocol metadata, invisible in most UIs.

Why it matters: a poisoned popular server backdoors many victims at once, and a rug-pull defeats one-time review. As teams install servers via package runners with little scrutiny, the gateway becomes a software-supply-chain entry point into everything it fronts.

Check / mitigate: pin server versions/hashes; review tool descriptions as untrusted input and monitor them for drift; sandbox third-party servers; prefer first-party or vetted servers for anything touching money or sensitive data.

A10Missing audit logging / no attribution of agent actions
Medium impactCompliance

No tamper-evident record of which agent, acting on whose behalf, called which tool with what arguments and what result. You cannot answer "what did the agent actually do, and why." This is nearly universal in early deployments and acute in regulated sectors.

Why it matters: it is not exploited directly - it is the enabler. Every other item here becomes undetectable and unprovable without attributed logs; incident response is blind, breach scope cannot be established, and audits (SOC 2, GDPR, Nigeria's NDPA) fail on the "can you demonstrate what happened" question. It is the difference between "we contained it and can prove the blast radius" and "we have no idea."

Check / mitigate: log every tool call with identity (agent + on-behalf-of user), arguments, outcome, and timestamp; make the log immutable/append-only with retention; ensure it is sufficient to reconstruct an incident and to satisfy your compliance regime.
